# AGENTS.md — DNNLS exercise-development guidance

This repository contains lecture material and a parallel, discovery-led practical curriculum for the Deep Neural Networks and Learning Systems module. Before designing or revising a week, read `curriculum/module-map.md` and use the actual teaching plan for that week. Exercises should complement, strengthen, or make students experience the lecture ideas rather than merely repeat the lecture.

## Working conventions

Work directly on `main` unless explicitly asked otherwise. Before editing an existing file, fetch the current version from `main` and use its latest SHA. Preserve established filenames and numbering unless a reorganisation is explicitly requested.

The exercise terminology is fixed:
- **Experiment** = the complete student activity/document.
- **Prompt** = one query the student copies into Gemini.
- **Investigation** = the notebook output Gemini generates for one prompt. It may be one code cell, one short Markdown explanation followed by one code cell, or one Markdown-only cell when no computation is needed.

Investigation numbers are global across the shared notebook and never reset between experiments. Optional explanatory Markdown that precedes code is part of the same investigation and does not receive a separate number. Handouts should refer to "the investigation generated by Prompt N in this experiment" or, when the student must edit code, "the code cell generated by Prompt N in this experiment".

## Exercise-document structure

Every student-facing experiment should normally include:
- title framed as a concrete question;
- **Dataset**;
- **Key concepts**;
- **Expected computational budget**;
- **Recommended runtime**;
- the standard copy/paste instruction and warning not to read ahead;
- a sequence of concrete Gemini prompts;
- questions after every prompt;
- exactly one **Try it yourself manually** section where the student edits code without asking Gemini;
- a late **Reveal: what was this experiment really about?** section;
- a final Gemini discussion prompt grounded in the evidence produced;
- final discussion questions.

Do not reveal the hidden objective too early. Prefer the learning sequence:
**observe → question → experiment → explanation → terminology**.

## Gemini notebook instructions

Each week has a notebook-level Gemini instruction file. Keep the **entire instruction file safely below 4,500 characters**; aim around 3,500–4,000 and check the actual file size after editing. Preserve one-investigation-per-prompt discipline, global investigation numbering, simple implementations, concise student-facing explanations, and the week's conceptual boundaries.

Allowed response forms for one prompt are:
1. one executable Python code cell;
2. one **short** explanatory Markdown cell followed by one code cell; or
3. one Markdown-only cell when no computation is needed.

Do not allow extra cells beyond those forms. Markdown should be used selectively when notation, equations, or a concise conceptual explanation materially improve understanding. Use valid Colab Markdown/LaTeX (`$...$`, `$$...$$`) so equations render correctly. In a Markdown+code investigation, only the code cell carries `# INVESTIGATION N`; the Markdown is part of the same investigation. A Markdown-only investigation should identify `INVESTIGATION N` at the top. Fixes/modifications replace the current investigation and keep its number.

Gemini should act more like a **runtime / well-briefed teaching assistant** than a lecturer. It may handle data loading, plotting, device setup and boilerplate, but the student's intellectual loop should remain visible.

When Gemini creates an important classifier, model, loss, update rule, representation or component, the copied student prompt should usually ask it to **briefly explain what it created**, its important inputs/outputs, and the role of the main parameters. Do not make every prompt explanation-heavy.

Use comments as teaching material. Prefer a few meaningful markers such as:
- `# KEY:` for a line the student should understand;
- `# TRY:` for a safe intervention.

## Experimental design principles

Expose one new mechanism at a time and shield incidental complexity. A useful criterion is:
**complexity of intervention << depth of phenomenon revealed**.

Use the simplest dataset that makes a phenomenon undeniable. Synthetic data and MNIST are often preferable early; StoryReasoning becomes useful when the real multimodal/system context adds educational value.

Expensive computation should happen once where possible. Record checkpoints, predictions, activations and metrics during that run so later prompts can analyse saved state instead of retraining.

Manual code involvement is mandatory even when Gemini generated the cell. Do not turn the notebook into a polished app that students only operate.

Interactivity and animation are allowed and often useful. Gemini may suggest them when they reveal a continuous relationship or training trajectory particularly well, but **interactivity should supplement code manipulation, not replace it**. Prefer direct variable editing when that is already simple and pedagogically useful. Do not rerun expensive training on every slider movement; animate or scrub saved states instead.

## Architecture exposure

Do not dump a full architecture on students and tell them to ignore most of it. Omit components until they matter.

General rule:
**Students should generate the part they are currently learning and inherit the parts they are not.**

Progressive exposure currently intended:
- Weeks 1–2: no real assessment architecture; establish clean phenomena first.
- Week 3: first tiny generic architecture only, e.g. `input → hidden layer → output`.
- Week 4: first simplified introduction of the assessment task/architecture and system diagnostics.
- Later weeks: expose or replace one relevant component at a time (visual encoder, language encoder, attention/fusion, generative components, etc.).
- Assessment: provide a canonical full architecture so all students start from the same system; ask them to diagnose, modify and justify components rather than regenerate the whole model.

Week 4 establishes an important boundary for later development: students meet StoryReasoning first through raw-frame floors/metric failures and through an annotation-only character-history subtask. Do **not** introduce a hidden CNN/CLIP encoder merely to enable frame retrieval at this point. Raw-image representation becomes a motivated problem for Week 5. In the Week 4 character task, persistent character IDs are metadata for constructing histories, not predictive input features.

Week 5 introduces the first learned visual component: students build a modest convolutional encoder/autoencoder, train it once by reconstruction, then freeze it and reuse cached latent vectors for simple visual retrieval. Keep the decoder as concise scaffolding around the studied encoder. Retrieval may compare candidate frames by visual similarity, but must **not** introduce a trained next-frame predictor, recurrent sequence model, attention, multimodal fusion or language encoder yet. The intended endpoint is that students can distinguish visual representation from temporal/story reasoning.

Week 6 focuses on evidence about representations and predictions. Students may use gradient/Integrated-Gradient attribution, perturbation/permutation controls, local surrogates, counterfactuals, probes and interventions. A frozen pretrained visual encoder may be introduced for transfer/probing on StoryReasoning, but probe performance must be described as **decodability**, not automatically as causal use or mechanistic understanding. Keep sequence memory, attention and multimodal fusion for later weeks; Week 6 should make students sceptical of explanations that are not tested against controls.

A useful exercise pattern is: **provided system → missing/changing component → observable consequence**.

## Pedagogical continuity

Important recurring ideas to preserve across weeks include:
- loss as specification, not merely a score;
- baselines/floors and "better than what?";
- checking whether predictions actually depend on the intended input;
- shuffled/permuted controls;
- representation geometry;
- training trajectories rather than only final metrics;
- distinguishing objective mismatch, optimisation failure, representation failure and generalisation failure.

Use `ARCHITECTURE_NARRATIVE.md` as the primary StoryReasoning architecture reference from Week 4 onward. It is a pedagogical reorganisation of the system's development, not merely a changelog. The older architecture-evolution document may be consulted for historical detail, but it must not override the narrative's conceptual order.

## Lecture-note conventions

Lecture notes live in `lecture_notes/`, with one LaTeX chapter per teaching week and a separate architecture overview chapter that acts as the running case-study reference.

For each weekly chapter:
- follow `curriculum/module-map.md` first and use `curriculum/learning-thread.md` to preserve conceptual continuity;
- aim for roughly **12–15 compiled pages**, favouring clear explanation over encyclopedic coverage;
- write in a scientific but engaging style: concrete observations, explicit questions, economical mathematics, and mechanistic explanations rather than textbook boilerplate;
- use the practical experiments as complementary evidence, not material to duplicate;
- keep optional mathematics or standard coding in clearly marked optional boxes;
- use **PyTorch** boxes only where code helps connect notation to implementation, and show only the important lines;
- include a compact **Application to the architecture** box focused on one mechanism or phenomenon relevant to the week's concepts;
- add figure placeholders only when a figure would genuinely help. Use the shared `\figureaction{...}` placeholder with a real caption and an explicit `ACTION` description; never reference an image file that does not yet exist;
- introduce terminology after the motivating problem where possible, and protect later weeks from premature detail.

The architecture overview may show the full system at a high level, but weekly chapters should unpack it progressively rather than repeatedly explaining the entire architecture.
